# Live acceptance: setup build context — progress

Fourth live acceptance run. Its subject is the one capability `SBC-1..SBC-6` added: **a setup recipe
that reads the package's own bytes** — `trust-store.export-certificates@1` writing into a working
copy that `docker.build@1` then builds. Methodology unchanged:
[DESIGN-live-acceptance-v1.md](DESIGN-live-acceptance-v1.md) governs; the
[v1](PROGRESS-live-acceptance.md), [v2](PROGRESS-live-acceptance-v2.md) and
[v3](PROGRESS-live-acceptance-v3.md) records are the prior runs this one is read against, and none of
them is ever rewritten. Finding ids continue the shared register at `LAF-51`; stressors at `LAS-49`.

**Status: agent scope complete; re-run after `SBC-9` is green.** Both routes were walked end to end
and diffed. Eleven findings, one of which — `LAF-51` — made the guided route unreachable on the code
as it stood and had to be worked around to run anything else; the workaround is stated in full below,
and `SBC-9` has since closed it, with the affected scenarios re-walked on unpatched code. One comparison (`LAB-C-03`) is weakened
rather than blocked, because the agent does not type secrets: a pass with a real typed token remains
human-gated. Nothing found here was fixed during the run.

## What makes this run different

The three prior runs asked whether a command works. This one asks whether **two routes agree**. The
design claims that the declarative recipe and the hand-written `SETUP.md` reach the same machine
state, and that claim has until now been made only in prose:

1. **Both routes are walked to the end**, on one machine, and their results are diffed — image id,
   image tag, keychain item, shell block, `.mcp.json` entry.
2. **Nothing is hermetic.** A real Docker daemon builds a real image from a real Dockerfile, and the
   certificate comes out of a real macOS keychain through `/usr/bin/security`.
3. **The refusals are again the feature.** No `docker`, no daemon, a `subject_contains` that matches
   nothing, and a `RUN` that fails must each stop the run and say which of them happened.

| `LAF-51` | **critical** | `LAB-A-02` | none — the ordinary path | `protocol/registry_index._index_artifact` ↔ `setup_engine/application._prepare_setup_plan` | **The compiled capability evidence and the consumer's recomputed capability set speak different vocabularies, so setup planning refuses almost every recipe.** The registry index publishes the recipe's *declared* capabilities (`docker`, `filesystem`, `keychain`, `network`, `process`, `trust-store` — the vocabulary the recipe parser validates against). The consumer recomputes them with `_planned_capabilities`, which emits the *policy* vocabulary (`docker-build`, `managed-file`, `keychain`, `network`, `process`, `trust-store`). `_prepare_setup_plan` requires the two to be **equal**. They cannot be, for any recipe that touches a file or a container: `filesystem` ≠ `managed-file`, `docker` ≠ `docker-pull`/`docker-build`. The only recipes that can plan are those whose entire capability need is `keychain` — nothing else in the module catalog is reachable through a registry. No recipe can satisfy both gates at once, because declaring `managed-file` is refused at parse time as an unknown capability. The failure surfaces as `Setup: planned=0, failures=1` with no reason on stdout; the reason is `compiled setup recipe, platform, or capability evidence does not match the object`, and is visible only under `--json` | `registry init`/`scaffold` an artifact whose recipe uses `shell.env-from-keychain@1`; `lock`, `build`, add the source, `marketplace install --yes`; setup never plans | every setup-bearing artifact delivered through a registry index except a keychain-only recipe — `2.4.0` and this branch alike |

| `LAF-55` | major | `LAB-A-05` | `LAS-50` | `setup_runtime._keychain_apply` | **With no terminal, the Keychain step stores an empty secret and reports success.** `security add-generic-password -w` prompts on the terminal; with stdin at `/dev/null` it prints `password data for new item: retype password for new item:` and exits 0 having stored an empty value. | `LAF-56` | major | `LAB-B-02` | `LAS-51` | `docs/protocol/setup-recipe-v2.md` manual equivalent ↔ `io/object_store` payload modes | **The documented manual build cannot be run as documented.** The reference tells the reader to `cp -R <package>/payload /tmp/aart-build && cd /tmp/aart-build`, then write the certificate into it. ### The patched executable, and why

`LAF-51` blocks every remaining scenario: on the shipped code no recipe beyond a keychain-only one can

## Clusters

Five clusters, not ten problems.

**1. The guided route does not run at all** — `LAF-51`, and `LAF-60` behind it. Two functions
disagree about what a capability is called, and the gate between them demands equality. Nothing else
in this document could be observed until that was worked around. It is a handful of lines, and it is
the difference between a feature and a feature that has never been run end to end by anyone. `LAF-60`
is its release-facing twin: whatever is decided, an older consumer's whole view of a registry stops
at the first artifact using a new module, and that belongs in the compatibility note rather than the
advice currently in `setup-recipe-v2.md`.

**2. The engine computes a review nobody sees** — `LAF-54`, `LAF-52`, `LAF-59`. The same defect at
three points: effects, failures, and transcripts are all assembled correctly and then dropped by the
presentation layer, which prints counts. `SBC-5` built the review and tested its *contents*; no test
asserts that a CLI path prints it, so it never did. A consumer approving effects with
`--approve-setup-effects` is approving a list they were shown only if they asked for `--json`.

**3. Recovery is promised in the review and delivered only inside a failing run** — `LAF-53`,
`LAF-58`. Every effect says `removes only changes created by this run`; uninstall says
`setup skipped`; a pre-existing tag keeps its name and loses its meaning. Either the wording is
narrowed to what rollback really is, or setup gains an undo. The receipt already contains everything
an undo would need, which suggests the second is not far off.

**4. The manual route is equal in intent and not in practice** — `LAF-56`, `LAF-57`. It had never
been executed before this run. The documented `cp -R` cannot work against a read-only object store,
and the two routes produce images that differ in mode bits, mtimes and manifest shape while agreeing
byte for byte on contents. The first is a one-word fix; the second is a decision about what "the same
image" is allowed to mean.

**5. An unattended install stores an empty secret and calls itself configured** — `LAF-55`. Alone,
and the one finding that produces a silently broken machine rather than a visible failure. A
non-interactive `security add-generic-password -w` succeeds with an empty value, and every check
downstream agrees the item exists.

### What this means for `SBC-8`

The plan's exit condition for `SBC-7` is "both routes complete, the comparison holds or every
difference is filed". Both routes completed and every difference is filed — but only cluster 1's
workaround made the first half possible, so **the honest reading is that the exit condition is met
for the run and not for the product**. Releasing `2.5.0` with `LAF-51` open would ship a headline
capability that cannot be invoked through any supported path. The sequencing decision — fix cluster 1
(and, in the same breath, decide clusters 2 and 3) before the release commit, or release and follow
with `2.5.1` — is the maintainer's.

### A methodology note

`security` resolves its keychain search list from the **caller's `HOME`**. Under the sandbox `HOME`
the user domain starts empty, so `find-certificate` and `find-generic-password` find nothing and
`list-keychains -d user -s …` writes into the sandbox's preferences. AART runs `security` with a
minimal environment and *no* `HOME`, which resolves to the real user's list. Every keychain
observation in this run is therefore made with the real `HOME`; the first apply attempt failed for
exactly this reason and is not a product finding.
